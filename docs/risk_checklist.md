# 운영 리스크 체크리스트

이 문서는 GEO Weekly Tracker를 실제로 운영(특히 `MOCK_LLM=false`로 실측을 시작한 이후)하면서
주기적으로 점검해야 할 리스크를 체크리스트 형태로 모은 것이다. 각 항목은 "무엇을, 왜, 얼마나
자주, 확인되면 어떻게"를 담는다 — 상세 배경은 각 항목이 링크하는 문서를 본다.

## 1. LLM 세션 변동성 (같은 프롬프트, 다른 답변)

- [ ] **무엇**: 같은 프롬프트를 같은 주에 여러 번 실행해도(`REPEAT_COUNT`) 매번 다른 답변이
      나올 수 있다 — LLM 응답 자체의 확률적 변동성.
- [ ] **왜**: 한 번의 실행 결과만으로 그 주의 SOV를 판단하면 우연히 언급/미언급된 결과에 지표
      전체가 흔들린다. `REPEAT_COUNT`회 반복 후 평균化(mention_count 합산)로 이 노이즈를 줄인다
      (docs/metrics.md §1).
- [ ] **얼마나 자주**: 분기 1회, 또는 SOV 수치가 전주 대비 급변했을 때(`sov_delta`가 비정상적으로
      큰 경우) 그 즉시.
- [ ] **조정 기준**: `REPEAT_COUNT`(관리자 화면 Settings 또는 `PUT /batch-config`)를 늘리면
      노이즈는 줄지만 호출 수가 정비례로 늘어난다(`MAX_CALLS_PER_BATCH`와 충돌 가능). 같은 주 내
      반복 실행들의 mention_count 분산이 크다고 체감되면(예: 3회 중 1회만 언급) `REPEAT_COUNT`를
      5 정도로 올리는 것을 검토한다. 무조건 늘리기보다 호출 예산과의 트레이드오프로 판단한다.

## 2. CLI별 웹 검색 동작 차이

- [ ] **무엇**: 세 CLI가 웹 검색 활성화 방법과 "실제로 검색했는지" 판정 신뢰도가 다르다
      ([docs/llm_clis.md](llm_clis.md) §4 — Gemini CLI만 `stats.tools.google_web_search.count`로
      실제 호출 여부를 신뢰성 있게 확인 가능, 나머지 둘은 근사치).
- [ ] **왜**: `web_search_used` 필드를 프로바이더 간 단순 비교하면 이 비대칭 때문에 왜곡된
      결론(예: "Claude Code가 웹 검색을 더 많이 쓴다")을 낼 수 있다.
- [ ] **얼마나 자주**: 각 CLI의 메이저 버전 업데이트 시(§3과 연동), 또는 반기 1회 공식 문서
      재확인.
- [ ] **확인되면**: `docs/llm_clis.md` §4의 비교표를 갱신하고, 새로 신뢰성 있는 판정 방법이
      생겼다면 어댑터 파싱 로직에 반영을 검토한다(백로그 후보 — docs/backlog.md).

## 3. CLI 버전 업데이트 시 플래그 호환성

- [ ] **무엇**: CLI는 API보다 훨씬 자주 바뀐다 — 플래그가 추가/제거/이름 변경될 수 있다
      (`--bare`, `--output-format`, `-o`/`--output-last-message`, `--search` 등, docs/llm_clis.md
      상단 경고 참조).
- [ ] **왜**: 어댑터가 넘기는 플래그가 새 버전에서 무시되거나 오류를 내면, 배치 전체가
      `CLIProcessError`로 실패하기 시작한다.
- [ ] **얼마나 자주**: CLI를 수동으로 업데이트하기 전에 **매번**. 자동 업데이트(npm의 `-g` 전역
      설치가 별도 알림 없이 갱신되는 경우)가 있는지도 함께 확인한다.
- [ ] **버전 고정 권장 여부**: **권장한다.** `npm install -g @openai/codex@<고정버전>`처럼
      버전을 명시해 설치하고, 업데이트는 의도적으로 "새 버전 설치 → `claude/codex/gemini --help`로
      플래그 재확인 → `docs/llm_clis.md` 갱신 → 목 모드 스모크 테스트 → 실제 CLI 파일럿 1회"
      순서를 거친 뒤에만 진행한다. 프로덕션 배치 서버에서 예고 없이 자동 업데이트되지 않도록 한다.

## 4. 좌석 구독 자동화 사용에 대한 사내 IT/계약 조건

- [ ] **무엇**: Claude Code CLI/Codex CLI/Gemini CLI는 모두 "사람이 대화형으로 쓰는" 것을
      전제한 구독 좌석 제품이다. 이를 배치 자동화(비대화형, 정기 스케줄)로 호출하는 것이
      각 서비스의 이용약관/사내 라이선스 계약 범위 안에 있는지는 별도로 확인이 필요하다.
- [ ] **확인 담당**: _(미기재 — 담당자 이름을 채운다)_
- [ ] **확인 일자**: _(미기재 — 실제 확인한 날짜를 채운다)_
- [ ] **결론**: _(미기재 — "가능"/"조건부 가능"/"불가, 대안 필요" 중 기록)_
- [ ] **얼마나 자주 재확인**: 각 CLI 제공사의 이용약관이 개정될 때, 또는 연 1회. 실측
      배치(`MOCK_LLM=false`)를 처음 승인하기 전에 반드시 1차 확인을 완료한다.

## 5. 인증 토큰 만료 모니터링

- [ ] **무엇**: 세 CLI 모두 완전 무인 재인증이 불가능하다 — 토큰 만료 시 사람이 개입해야 한다
      (docs/operations.md §4).
- [ ] **왜**: 특정 프로바이더에서 `MissingAPIKeyError`가 계속 발생하면 그 채널의 주간 데이터가
      통째로 비게 되고, `weekly_snapshot`의 해당 프로바이더 스코프가 0/NULL로 채워져 지표가
      왜곡된다.
- [ ] **얼마나 자주**: 매 배치 실행 후 `GET /runs/{batch_id}/status`의 `failed` 건수 확인이
      1차 방어선. 토큰 자체의 만료 예정일을 캘린더에 등록해두는 것을 권장한다.
- [ ] **확인되면**: docs/operations.md §1~3의 재인증 절차를 그 CLI에 대해 수행한다.

## 6. 브랜드 매칭 오탐/누락 검수

- [ ] **무엇**: 별칭 기반 텍스트 매칭(`app/services/brand_matching.py`)은 규칙 기반이라 과매칭
      (다른 고유명사를 브랜드로 오인)/누락(등록 안 된 표기)이 있을 수 있다.
- [ ] **왜**: `mention`/`weekly_snapshot`의 정확도가 이 매칭 품질에 직접 의존한다.
- [ ] **얼마나 자주**: 배치 직후 최소 1회, 신규 브랜드/별칭 추가 직후는 반드시.
- [ ] **확인되면**: `brand_alias`/`brand_domain`을 관리 API로 보정한다(docs/api.md §2).

## 7. `raw_response` 보관·저작권 정책 준수

- [ ] **무엇**: docs/metrics.md §6에서 확정한 방침(무기한 보존, 사내 열람 전용, 외부 재게시
      금지)이 실제 화면/배포 산출물에서 지켜지고 있는지.
- [ ] **왜**: 프론트엔드나 리포트 내보내기(`GET /export/csv` 등)에 원문이 의도치 않게 외부로
      나가는 경로가 생기면 정책 위반이다.
- [ ] **얼마나 자주**: 새 화면(특히 "공유"/"내보내기"/"공개 링크" 류 기능)을 추가할 때마다.
- [ ] **확인되면**: docs/metrics.md §6을 먼저 갱신(정책 변경)한 뒤 코드에 반영한다.

## 8. worker 데몬은 정확히 1개 인스턴스만 떠야 한다

- [ ] **무엇**: `app/worker/daemon.py`가 여러 인스턴스로 동시에 뜨면 같은 PENDING 잡을 중복
      실행할 수 있다(migration_flask_postgres.md §2.3).
- [ ] **왜**: systemd 유닛(`geo-tracker-worker.service`)은 기본적으로 유닛 하나당 프로세스
      하나만 관리하므로 정상 운영에서는 자연히 지켜지지만, 배포 스크립트를 잘못 만들어 같은
      유닛을 두 서버에서 각각 enable하거나, 수동으로 `python -m app.worker.daemon`을 터미널에서
      추가로 띄우면 이 전제가 깨진다.
- [ ] **얼마나 자주**: 배포/서버 이전 직후, 또는 배치가 이상하게 두 배 빠르게 처리되는 것처럼
      보일 때(중복 실행 의심 신호).
- [ ] **확인되면**: `systemctl status geo-tracker-worker`로 인스턴스가 하나인지 확인하고, 다른
      서버/터미널에 떠 있는 프로세스가 있으면 중지한다.

## 9. Node.js 설치 방식(nvm vs 시스템 전역)이 systemd PATH를 깨뜨릴 수 있다

- [ ] **무엇**: `geo-tracker-worker.service`의 `Environment=PATH=...`는 Codex/Gemini CLI가
      설치된 실제 경로를 하드코딩한다. nvm으로 Node.js를 설치했다면 그 경로에 Node 버전 문자열이
      포함되므로(`~/.nvm/versions/node/<버전>/bin`), Node를 업그레이드하면 이 경로가 깨진다.
- [ ] **왜**: PATH가 깨지면 worker 데몬이 `shutil.which()`로 CLI를 찾지 못해
      `MissingAPIKeyError`로 즉시 실패하고, 그 실패가 "인증 문제"로 오인되어 엉뚱한 곳(로그인
      재확인)에서 시간을 쓸 수 있다.
- [ ] **얼마나 자주**: Node.js를 업그레이드할 때마다(nvm 사용 시 특히), 또는 배치 전체가 특정
      프로바이더에서만 갑자기 100% 실패하기 시작했을 때.
- [ ] **확인되면**: 가능하면 시스템 전역 Node.js(NodeSource apt 등, 경로 고정)로 재설치해 이
      문제 자체를 없애는 것을 권장한다(docs/deployment.md §사전 준비 참조). nvm을 계속 써야
      한다면 Node 업그레이드 직후 `geo-tracker-worker.service`의 `Environment=PATH=...`를
      갱신하고 `systemctl daemon-reload && systemctl restart geo-tracker-worker`.

## 10. Ubuntu 헤드리스 서버에서 CLI 최초 로그인이 가능한지 미검증

- [ ] **무엇**: 세 CLI의 OAuth 로그인 플로우("다른 기기 브라우저로 URL 열고 코드 붙여넣기")가
      GUI 없는 Ubuntu 서버에서 실제로 동작하는지 아직 실측하지 않았다(docs/llm_clis.md §7.5).
- [ ] **왜**: 로그인 자체가 안 되면 그 CLI 채널은 처음부터 측정이 불가능하다.
- [ ] **얼마나 자주**: Phase 8(실 CLI 파일럿) 착수 시 1회, 이후 토큰 재발급/서버 재설치 시마다.
- [ ] **확인되면**: docs/operations.md에 실제로 동작한 절차를 기록한다. 안 되는 CLI가 있으면
      로컬 PC에서 로그인 후 자격증명 파일을 서버로 옮기는 대안을 검토하고 절차를 문서화한다.
